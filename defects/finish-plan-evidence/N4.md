## Change
The follow-up (2nd message) DUE cutoff is now the ACTIVE `lead_followup` automation's
`wait_hours` for the profile (hours → ms), falling back to 72h when the value is missing or 0.
The exported `FOLLOWUP_AFTER_MS` constant is kept only as a deprecated 72h alias.

- `src/server/catchup-followup.ts`:
  - `FOLLOWUP_AFTER_MS = 72 * 60 * 60_000` (deprecated alias, was `24 * 60 * 60_000`).
  - `resolveWaitHours(waitHours?)` → `wait_hours` when > 0, else `DEFAULT_FOLLOWUP_WAIT_HOURS` (72).
  - `gatherFollowupCandidates` takes `waitHours?: number`; `dueCutoffMs = waitHours * 60 * 60_000`.
  - Due filter uses `t + dueCutoffMs <= now`. Not-yet-due active leads are pushed to `dropped`
    with reason `not yet due (<n>h)` (COUNTED, not silent), carrying leadType/createdUtc/leadSource.
  - `anniversaryMs = created + dueCutoffMs`.
  - `FollowupGatherResult.waitHours: number` added and returned via `base`.
- `scripts/catchup-followup.ts`:
  - passes `waitHours: followup.wait_hours` to the gather.
  - dry-run header line `due cutoff:  <n>h (lead_followup wait_hours; 72h fallback)`.
  - counts label renamed `due(24h)=` → `due=`.
  - CSV summary gains `dueCutoffHours: res.waitHours`.
- `src/test/catchup-followup.test.ts`: existing tests tuned to a 24h anniversary now pass
  `waitHours: 24` explicitly (intent preserved); anniversary test rewritten to an 80h lead at
  the 72h default; new N4 describe block added.
