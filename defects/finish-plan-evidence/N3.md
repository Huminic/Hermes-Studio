# N3 — real wiring (audience config + UI, scheduler, alerts routing, weekend windows)

Builder evidence for NIGHT TRANCHE 3 (N3.1–N3.5). Context: N2 + N2.6 gave the
four deliveries as CLI scripts with `--to`. Duane's decision: ONE management
audience per store (Duane, Durran, Don, Shelby) receives every report, the
wrap-up text, the intro text and the alerts. Customer texting untouched. Same
rules: no docker, no sends, no push, no crontab EDITS (a cron FILE is added to
the repo; Major installs it).

## What was built

- **N3.1** `comms.management_audience {emails, cells(E.164)}`, `comms.reports
  {enabled, tz, store_name}`, `comms.alerts {enabled}`, `comms.holidays`,
  `comms.agent_name` added to `CommsSchema`. `readManagementAudience` /
  `updateManagementAudience` server helpers. `/api/customer/notifications` GET/PUT
  round-trips the audience + switches (validates emails + E.164). A "Management
  audience" card (two textareas + two toggles) added to the customer notifications
  settings page. Every `scripts/send-*.ts` defaults `--to` to the store's
  management audience (emails for email reports, cells for texts) and
  `--store-name` to `comms.reports.store_name` (via `scripts/report-recipients.ts`);
  explicit flags still override.
- **N3.2** `computeReportWindow()` (pure, exported) — MORNING window now runs from
  the previous business-day CLOSE (Mon–Sat, Sunday/holidays skipped) to report-day
  OPEN, so Monday covers Saturday 19:00 → Monday 08:00 and never repeats
  Saturday's wrap-up. WRAP-UP unchanged (report-day OPEN → now). Lead Source
  windows unchanged. raw-counts records both bounds.
- **N3.3** `scripts/cron-serra-reports.sh` — docker-exec wrapper (like
  cron-catchup-followup.sh) taking `<job> ∈ morning|noon|wrapup|text|snapshot`,
  iterating `REPORT_PROFILES` (default EMPTY). Per profile+job: gate on
  reports.enabled + non-empty audience (`scripts/report-gate.ts`, exit 0/10), run
  comms-preview for the right window into `/tmp/reports/<profile>/<date>/`, then
  the matching send-*.ts with `--send`; one log line per profile per job.
  `docs/serra-reports-cron.txt` — exact Mon–Sat crontab lines (morning 13:00,
  noon 17:00, wrapup 23:30, text 00:00, snapshot 04:00 UTC). No crontab edit.
- **N3.4** `src/server/lead-alert-dispatch.ts` (`dispatchLeadAlerts`) — gated by
  `comms.alerts.enabled`, delivered ONLY inside business hours, deduped by
  (profile, bucket, leadId) per day, addressed to `management_audience.emails`
  with subject `Lead alert — <Store>: <n> leads need attention` and a short table
  (lead · source · waiting · status · bucket) via the shared report-email
  template. Registered per profile as `leadAgingAlertCheck` in
  `sentinel.DEFAULT_CHECKS` (VIN pull is lazy — only after the gates pass;
  `lead_notify_log` dedup marker; `sendNotification` email; best-effort
  `findStaleStatus` for "same status >1 week" once 8 daily snapshots exist).
  `scripts/lead-status-snapshot.ts` — the nightly snapshot CLI over the existing
  `runLeadStatusSnapshot`.
- **N3.5** `send-intro-text.ts` records each (profile, cell) it texts via the
  `lead_notify_log` marker (`introMarkerKey`) and drops any cell already
  introduced unless `--force`; the marker is stamped only for cells that went out
  (dry-run never stamps).

## Notes / carried decisions (truth-over-compliance)

- **Alerts to management, not operator.** `leadAgingAlertCheck` returns `[]` to
  the generic Sentinel feed and delivers its OWN store-addressed email to
  `management_audience.emails` — so a store's lead alerts never land in the
  operator's generic Sentinel batch. This is the faithful reading of "deliver
  through the existing sentinel alert path but addressed to management_audience".
- **`store_name` extension.** The plan's `comms.reports` block was `{enabled, tz}`;
  a `store_name` field was added so the scheduler can fill report subjects/headers
  without a per-invocation flag (falls back to the profile slug). Small, schema-
  validated, and only read by the send scripts.
- **`same status >1 week`.** Wired via the existing `findStaleStatus` over 8 daily
  snapshots; returns empty until a week of nightly snapshots accumulates (the
  snapshot job starts producing them now). Recorded honestly rather than faked.
- **Lead-alert names.** The sentinel check does not run the capped/heavy broker
  name resolution on every pass; alert rows fall back to `Lead <id>` when a first
  name is not already on the lead record (never a fabricated name).
- **Text-job weekday.** 00:00 UTC is the next UTC day, so the text crontab line
  uses `2-6`; the Saturday-evening text is therefore not sent by the default line
  (documented in docs/serra-reports-cron.txt with how to opt in).
